# Validation plan: the memory rule on cgroup v2 under real systemd

**Status: a plan and a written, unit-tested harness. Nothing has been run under systemd.** `docs/MEMORY_MONITOR_RULE.md` marks the rule as verified only on synthetic v2 files and on real workloads under cgroup v1 without systemd. This plan closes that gap on a disposable machine with generated data only.
It deploys nothing, touches no existing service, running broadcast or real season data, and sends nothing anywhere.

**Revision note.** This replaces the earlier five-stage plan. It is narrowed to the four checks V1-V4, the load is injected into the daemon's own cgroup, and the estimate-error measurement is removed (section 2). **V0** (the setup is what the design says: dedicated unprivileged service user, production sandbox and permissions, marker order) was added later; it measures nothing about the memory rule.

## 0. Pins, entry, exit, stop

* **Candidate pin:** `ecf62ea6c709903ff6a6eb8d95426834803da8dc` (candidate 3; unvalidated; candidates 1 and 2 are preserved unchanged), recorded in `tools/vtest/PIN`. The harness extracts exactly that tree with `git archive` and verifies it blob by blob, so harness commits made on top do not change the code under test.
* **Entry:** the owner approves the plan, names the machine, and approves any cost (section 6). Nothing starts before that.
* **Stop on failure:** the run stops at the first stage that does not pass. Nothing is cleaned up; evidence is preserved; a later run is refused until the stop is acknowledged with a recorded reason. `invalid` (the workload did not do what the test needs) is not a pass.
* **Exit:** a report (section 8) with each check pass, fail, invalid or not run, the raw samples, and a manifest of hashes.
* **Abort at once:** any write outside the harness paths, free disk under 4 GiB, or any route to another host.

## 1. The stages

| Stage | Question | Checks (summary) |
|---|---|---|
| **V0** | Is the setup what the design says it is? | **Measures nothing about the memory rule.** Daemon and monitor run as a dedicated unprivileged user (no login, no extra groups, not root or nobody) under the template's sandbox (`ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`, `NoNewPrivileges`, only the store, public folder and guard folder writable, code read-only). Owners and modes of the folders are judged (the service user owns its store, the public folder and the guard; the rest is root's). Systemd's *applied* properties and the running processes' uid, gid, capabilities and `NoNewPrivs` must agree with the unit files. Run as that user, creating a file works in the three folders and is refused everywhere else the harness or units keep things. The **harness (root) collects the kernel log itself**; whether the service user can read it is recorded only (production: probably not, so an incident record may say the victim is unknown). A clean stop closes the run marker; a start opens one for **this** invocation before the daemon's main process starts. **Durability probe** (strace of the real start gate and stop hook, as the service user, in scratch folders): the marker is written as file, fsync, rename, fsync of the folder; removed as unlink, fsync of the folder; removed only after an OOM incident is durable; left alone when a stop could not be accounted for. This shows the **order of the program's own system calls**, not that the disk honoured them. |
| **V1** | Does real cache growth cause a false trip? | Clean file cache fills the daemon's cgroup to its limit for at least 30 min (invalid if it does not). No trip, no `oom_kill`, no restart, loader still reading; the kernel was demonstrably reclaiming; heartbeat breakdown present and consistent. **Broadcast performance is judged directly** (lease, publication deadlines, publication errors; clock stand-stills and tick age are reported, not gated) in two separate phases, publication-only then cache stress; pressure is a recorded diagnostic and does not decide. Criteria: `docs/MEMORY_MONITOR_VALIDATION_CRITERIA.md` (supersedes the earlier "pressure stays low" gate). |
| **V2a** | Does sustained anonymous memory trip as designed? | Anonymous load to 93 % of `MemoryMax`, held. Latch kind `memory_high` from the monitor 58-90 s after the 90 % line is crossed, before any kill; evidence has the breakdown; daemon paused and its clock stopped. |
| **V2b / V2c** | What happens on an OOM, and is the daemon's own death recovered from? | **V2b**: load to 3x the limit; the kernel picks its victim (normally the injected load). **V2c**: the same in an isolated scenario where the **daemon** is made the preferred victim (section 3), with a bounded load (1.5x the limit). Both: kernel kill seen; systemd recognises the OOM; with `OOMPolicy=stop` no process of the unit survives; the unit restarts as configured; public files intact; clock continues. **Required in both: a persistent incident record and a hold**: a latch with new evidence exists, the daemon stays paused, the clock does not advance and the latch is unchanged over 15 s. An OOM that leaves no latch **fails V2**. **The lifecycle design is judged too** (candidate 3, `docs/OOM_INCIDENT_RECORD.md`): the latch must be written by the unit's stop hook (`oom_kill`, source `systemd`; an `unaccounted_stop` latch means only the start gate's fail-safe caught it, which fails), before the restarted daemon became active, as exactly one new `trips.jsonl` line, with the run marker closed and a new one opened after the latch, and the victim recorded explicitly (`identified` or `unknown`, never guessed) without contradicting the kernel log. **The victim is reported** from the kernel log. **`V2.daemon_oom_exercised` passes only with kernel evidence that the daemon itself was killed**; otherwise it is **incomplete (not_run), never pass**, and V2 is not a pass. |
| **V3** | Monitor dies or hangs | `kill -9` (V3a): restarts in time, no trip. Stop (V3b) and `SIGSTOP` hang (V3c): the daemon trips itself (`monitor_silent`, source daemon) within the stale limit and pauses safely; recoverable by the documented `release` and `resume`. Repeated monitor OOM until the start limit leaves the unit failed (V3d): the daemon trips. After V3a-V3d the daemon's own run is untouched (same process, same run marker) and no `oom_kill` / `unaccounted_stop` line was written. **V3e is the negative control for the daemon's hooks**: `kill -9`, `systemctl restart`, and stop-then-start of the daemon, none of which is an OOM, must record nothing (no latch, no incident line, no `PAUSE`, clock advances) while the stop hook closes the run marker and the start gate opens a new one. |
| **V4** | Does a latch survive restarts? | With an existing latch: daemon restart, monitor restart, both in each order, `kill -9` of each: latch byte-identical, daemon still paused, clock stopped, public files unchanged, `resume` refused. Refusals (`resume` rc 3, short reason rc 2, stale heartbeat rc 4). Documented `release` keeps the latch in `evidence/released/`, deletes nothing, and `resume` then works. Every disturbance must also leave `trips.jsonl` unchanged and close and reopen the daemon's run marker (a monitor-only disturbance leaves the same marker). **Failure injection (`V4.immutable_guard`)**: the guard folder is made immutable (`chattr +i`, removed in a `finally`) and a bounded OOM stops the daemon: no new daemon may run over the unrecorded incident (the start gate refuses), `PAUSE` holds, the marker stays open, the journal shows the refusal; once the folder is writable again the unit starts **held** with an `unaccounted_stop` latch that names the previous run, and `release` + `resume` clear it. **This is its own scenario, not proof of equivalent full-disk behaviour:** it makes every create, rename and unlink in the folder fail with a permission error (EPERM), whereas a full disk gives ENOSPC and can leave partial writes; the partial-write case is covered only by a local test on a 48 KiB tmpfs. A second trip makes a second latch. Optional reboot phase: after a **clean reboot** the run marker must be closed before any unit starts (else every reboot would start held) and the start records nothing; after a **hard reset** (power cut, operator's act) the marker must still be there and the start must record exactly one `unaccounted_stop` saying the host restarted. |

Step ids in the harness (`V1.load`, `V2b.overrun`, ...) are the ids in `tools/vtest/stage_*.py`; a test checks the code and these steps do not drift apart. Exact settings are printed by `vtest.py plan`.

## 2. What V1 can and cannot measure

The kernel offers no exact "non-reclaimable footprint". The monitor's `pinned` is an **estimate** of it, built from `memory.stat`. Therefore:

* **Not claimed:** any estimation-error figure, or a ratio "estimate / truth". There is no truth value to compute it against.
* **Measured:** (a) a *controlled input*: the loader logs the bytes it read, the daemon's own anonymous memory is known, so the estimate must stay consistent with those (a consistency bound with a stated margin; it can fail, it cannot prove accuracy); (b) *reclaim activity*: `memory.events max`, `pgscan`, `pgsteal` rise, so the cache was really being reclaimed at the limit; (c) *reclaim probes*: `memory.reclaim` asks the kernel to give memory back (kernel 5.19+); what it returns is lower-bound evidence of reclaimable memory; (d) *pressure counters*: PSI is recorded as a diagnostic only (it is read from the daemon's cgroup, which also holds the loader, so it cannot be attributed to the daemon) and gates nothing; broadcast behaviour is judged by its own checks, see the criteria document; (e) *survival*: no trip, no kill, no restart, the workload still progressing.
* A pass says: on this kernel, with this workload, the old false-trip pattern did not recur and the estimate stayed consistent with a known input. It does not say the estimate is accurate in general. The original trip remains classified as "likely cache-related, not proven false".

## 3. Method

* **Injection into the daemon's cgroup.** Loaders join the daemon's cgroup through `cgroup.procs`, so the limit, OOM killer, `OOMPolicy` and the monitor's `--cgroup` path are the real ones. Limits and every restart and OOM setting of the units are unchanged from the templates (checked by `invariants`); only names, paths, loopback URL, user and the disk floor differ, and each difference is printed and recorded.
* **V2c: choosing the victim without making anything unkillable.** Before the load starts, `oom_score_adj` is **raised** to 1000 for the processes already inside the daemon's own disposable cgroup, so the kernel prefers them to the injected load, which keeps the default and stays killable. Rules, enforced in code (`Env.oom_adjust`) and tested: only values 0..1000 (never a value that makes a process unkillable), never lowered, only pids currently in `dfl-vtest-daemon.service`'s cgroup (not the monitor's, not the host's), and nothing persistent: a restarted daemon starts at its default, which V2c checks (`adjustment_not_persistent`). The load is bounded (1.5x `MemoryMax`, a finite wait of its own size over its rate plus 2 minutes, always stopped). The adjustment is read back; if it was not applied, V2c is `invalid`.
* **Sampler:** 1 Hz JSONL of `memory.current/max/stat/events/pressure` and the monitor's own estimate, using the pinned monitor's reader. It tolerates the cgroup disappearing.
* **Loaders** log ground truth every second (bytes read, bytes allocated, resident size).
* **Fixture:** a generated league and season (the repository's test generator), a loopback static server, no real data.
* **Smoke run first** (`run --smoke`): short settings, non-qualifying, to shake out harness faults before the real run. Its results are never reported as acceptance.

## 4. Known limits

* **OOM victim and incompleteness.** In the natural overrun (V2b) the kernel normally kills the injected load, which makes systemd stop and restart the unit (`OOMPolicy=stop`) but does not show that the daemon's own death is recovered from. V2c is the scenario that exercises it. The summary check `V2.daemon_oom_exercised` needs **kernel evidence naming the daemon** (a pid that was in its cgroup before the load) as an OOM victim; if the kernel log cannot be read, names another victim, uses a line format the parser does not know, or the selection step was not applied, the check is **incomplete** and V2 is not a pass. An incomplete stage stops a full run (anything but pass stops it); later stages can be run with `--stages V3,V4 --acknowledge-stop '<reason>'`.
* **Missing incident record is a defect, not a finding.** If V2b fails `incident_record_and_hold`, that is a defect of the candidate: it is fixed in a new, separately tested candidate with its own pin and a full re-run. The harness proposes no runtime fix and contains none. Whether the monitor misses the kill because the cgroup is recreated between its 10 s samples is a hypothesis the stage tests, not a known fact.
* Injected load stands in for a leak; it does not reproduce the daemon's own allocation behaviour.
* The harness has not run under systemd. Results are valid only for the machine, kernel and systemd version recorded.

## 5. Change impact: what to repeat

Documentation-only changes invalidate nothing. Otherwise (`vtest.py affected --recorded <rev>`):

| Change | Repeat |
|---|---|
| Code under test: the start gate, stop hook or daemon (`tools/broadcast_run.py`) | V0, V2, V3, V4 (the memory rule, V1, does not read it), **and it is a new candidate** with a new pin |
| Code under test: the monitor (`tools/rehearsal_check.py`), `src/`, the fixture generator, any other file under `tools/` or `deploy/` | all stages, **and a new candidate** |
| A unit template: comments only | none; a lifecycle directive (`ExecStartPre`, `ExecStopPost`, `OOMPolicy`, `Restart*`, `StartLimit*`, ...) V0, V2, V3, V4; a resource limit (`MemoryMax`, ...) all stages; anything else all stages |
| Harness: a stage's own steps | that stage |
| Harness: a judgment file used by some stages (`perms.py`, `durability.py` V0; `lifecycle.py` V2-V4) | those stages |
| Harness: shared machinery (`common.py`, `render.py`, `sampler.py`, `loaders.py`, `scenarios.py`, `PIN`, ...) | all stages |
| `docs/`, other tests, `vtest.py`, `preflight.py`, README | none |

Retests are chosen by the behaviour a change can affect, not by "everything again": `vtest.py affected --recorded <rev>` prints the stages and the reason for each file. A change to the lifecycle design is the case that justifies repeating the lifecycle stages.

## 6. Environment and minimum resources

No suitable environment exists in the session that prepared this plan: it runs under cgroup v1 with no systemd as PID 1 and no way to start a VM, so **the harness could not be executed here**. A disposable machine must be provided.

Minimum: 1 vCPU, 1 GiB RAM with swap off, 5 GiB free disk, kernel >= 5.4 (>= 5.19 for reclaim probes), systemd >= 243 as PID 1, writable cgroup v2 with the memory controller, `python3`, `git`, root; created for this test and not used for anything else. A cloud VM of this size costs money and needs the owner's explicit approval; a local VM or spare machine does not. The operator creates `/etc/dfl-vtest-disposable` by hand; without it the harness refuses to run. `vtest.py preflight` (read-only) reports READY or exactly what is missing.

### Privileges the harness needs (all on the disposable machine)

* **Two kinds of actor, kept apart.** The *services* (daemon, monitor) run as a dedicated unprivileged user the operator creates first (`dfl-vtest`: system user, no login, no extra groups, not root or nobody); the install sets owners and modes of the folders as the production design intends. The *harness* runs as root and is never a child of a service: it places loaders in the daemon's cgroup, collects the kernel log, runs `chattr`, controls the `dfl-vtest-*` units and runs the operator's documented commands (`release`, `resume`) **as the service user**. One shared service user mirrors the production templates (`dflv2` for daemon, monitor and supervisor); production separates a builder user, which the harness does not model (the harness, as root, plays the builder).
* **root** (the harness): units, cgroup control files, `/srv/dfl-vtest`, `/opt/dfl-vtest-src`, `/etc/dfl-vtest`, `chattr`, `strace`, `setpriv`.
* **V2c additionally:** write access to `/proc/<pid>/oom_score_adj` of processes in the daemon's test cgroup. **Raising** a value needs no capability beyond that write access; **lowering** would need `CAP_SYS_RESOURCE` and is refused by the harness anyway. No sysctl, cgroup setting or unit property is changed for this.
* **Read access to the kernel log for the harness** (`journalctl -k`, or `dmesg`; root). The service user need not have it: an incident record may say "victim unknown" in production. The test's victim comes from the harness's own collection; without it the victim is unknown to the test and the daemon-OOM check is incomplete.
* Nothing else: no network, no credentials, no other host, no change to the monitor's cgroup.

## 7. Isolation, rollback, evidence

* No real unit, path or data: preflight refuses a machine with real DFL units or paths. Writes are confined to `/srv/dfl-vtest`, `/opt/dfl-vtest-src`, `/etc/dfl-vtest` and `dfl-vtest-*` unit files; `systemctl` may change only `dfl-vtest-*` units; cgroup writes are limited to `memory.reclaim` and `cgroup.procs` of those units. Units are never enabled; nothing is installed to start at boot.
* Loopback only; no mail, alert or message of any kind.
* Nothing is deleted automatically. `teardown` needs `--yes` and keeps evidence unless told otherwise; the machine's own destruction is a manual step after the report is accepted.
* Each stage writes `result.json` and a `MANIFEST.sha256`. Evidence is reviewed before any of it leaves the machine, and is not published.

## 8. Report

The revision tested and the pin; the machine facts (`uname -r`, systemd version, controllers); every check with its status and deciding file; V1 stated as in section 2, with no error figure; trip times against the 58-90 s window; the V2b and V2c incident-record results, the reported OOM victims and the kernel lines that name them, and whether daemon-OOM validation is complete or incomplete; every deviation; and a recommendation. Delivered to the owner, who decides.

## 9. Not covered

Deployment itself; the real units' install, enable and boot ordering (a separate gate); a full-length broadcast; the engine's behaviour; public-folder capacity beyond the fixture; any change to limits.


## Lifecycle design (third candidate): what the harness judges, and what stays unverified

The pinned candidate (`tools/vtest/PIN`) carries an `ExecStartPre=` start gate and an `ExecStopPost=` stop hook around the daemon (`docs/OOM_INCIDENT_RECORD.md`). `vtest.py install` **refuses** a daemon unit that lacks them, strips them, loses the `ExecStartPre=` failure semantics (a `-` prefix), points the hook at another cgroup, or drops `OOMPolicy=stop` or `RequiresMountsFor=` in `[Unit]` (`render.lifecycle_problems`). The pure judgments are in `tools/vtest/lifecycle.py` and tested on synthetic values (`tests/test_vtest_lifecycle.py`).

**Still unverified until a run on a real machine:** that systemd runs the hook before `Restart=` and the gate before every start; that `$SERVICE_RESULT`, `$MAINPID` etc. are what the hook assumes; that `memory.events` is readable while the hook runs; that a clean shutdown runs `ExecStopPost=` to completion (the likeliest way the design could misbehave: the V4 clean-reboot check); that an immutable guard folder behaves as a full or read-only disk does for the hook and gate (it is a stand-in: `chattr +i` blocks creating, renaming and removing entries, but a file already in the folder can still be written in place); how the monitor's heartbeat behaves for those seconds. V0 now checks the service user's permissions, the applied sandbox and the marker order. **Still not covered:** a builder user separate from the daemon's user (the harness models the builder as root); production disk, mount and boot ordering; that the disk honours fsync (the durability probe shows only the order of the program's calls; a power cut on a running machine cannot be tested, and the hard-reset phase shows only that the marker survives a reset of the disposable machine); and the behaviour of a genuinely full disk (the immutable-folder scenario is a different fault: see V4).
