# Launch roadmap: one evidence table (2026-11-11)

Replaces `docs/COMPLETION_ROADMAP_2026-11-06.md` and `docs/ROADMAP.md` (both kept unchanged below a "superseded" banner as history). Every cell names a commit or a result file. A level is only claimed where a result exists for it; a blank is written as **none**.

**Levels.** *Implemented*: code is in the branch. *Locally tested*: automated tests or scratch runs on a build machine (no real systemd, no real host). *System-tested*: run on a real machine against the real thing it protects or runs under (real systemd, real Spaces, real host). *Deployed*: installed and in service on a host. Evidence for one commit is not evidence for another: the pin (`tools/vtest/PIN`, candidate `ecf62ea`) is the code the memory-rule validation is about.

**Integrated revision.** Branch `integration/launch-candidate-2026-11-11`. Layer 1, `ab87c22` (`backend/memory-monitor-vtest-2026-11-08` tip `baca129` + CI and installer test fixes): the pin gate is **green**. Layer 2, the tip: adds `eb05ac9` (Spaces recovery) and `d2e66bb` (fresh-rehearsal preparation, monitor live drill). Relative to the pin `ecf62ea` the branch **modifies no existing file outside `docs/` and `tests/`**; it only adds files (the harness `tools/vtest/`, `tools/recovery_run/`, `deploy/rehearsal/fresh_run.sh`, `tools/monitor_live_drill.py`). The harness's own rule counts any added file under `tools/` or `deploy/` as code under test, so the pin gate is **red at the tip** until the owner decides (section 3).
